# Project Constitution: Arduino Firmware

**Version:** 1.0.0  
**Ratification Date:** 2026-11-11  
**Last Amended Date:** 2026-11-11  

---

## Preamble

Ця конституція визначає архітектурні, технічні та етичні принципи розробки прошивки для мікроконтролерів Arduino у цьому проекті. Кожен учасник команди та автоматизований агент зобов'язані дотримуватися цих правил задля забезпечення стабільності, безпеки та передбачуваності пристрою на рівні «заліза» (hardware) та коду.

---

## Core Principles

### I. Hardware Safety & Protection (Апаратна безпека)
- **Правило:** Кожен рядок коду, що взаємодіє з пінами (GPIO, PWM, ADC/DAC), живленням чи периферією, **MUST** враховувати обмеження максимального струму, напруги та тепловиділення компонентів.
- **Обґрунтування:** Помилки в програмному забезпеченні на мікроконтролерах можуть призвести до фізичного пошкодження або виходу з ладу апаратної частини (перегрів, коротке замикання).

### II. Memory Efficiency (Ефективність пам'яті)
- **Правило:** Динамічне виділення пам'яті (`malloc`, `free`, `new`, `std::string` зі значною фрагментацією) **MUST NOT** використовуватися у робочому циклі прошивки (`loop()`, перериваннях). Вся пам'ять (RAM та Flash) **MUST** бути статично або попередньо розподіленою (static allocation).
- **Обґрунтування:** Arduino-сумісні плати мають критично обмежений об'єм оперативної пам'яті (RAM). Витік пам'яті (memory leak) чи фрагментація неминуче призводять до зависання пристрою (`Crash/Lockup`).

### III. Deterministic Real-Time Behavior (Детермінована поведінка в реальному часі)
- **Правило:** Використання блокуючих функцій, таких як необґрунтовані `delay()`, довгі цикли очікування без таймаутів або важкі операції в обробниках переривань (ISR), **MUST NOT** допускатися. Код **MUST** будуватися на неблокуючій логіці (state machines, `millis()`-based таймери).
- **Обґрунтування:** Затримки в основному циклі або перериваннях порушують роботу протоколів зв'язку та керування пінами в реальному часі.

### IV. Maintainable & Modular Architecture (Модульність та підтримка)
- **Правило:** Драйвери периферії та бізнес-логіка **MUST** бути чітко відокремленими. Кожен модуль (сенсор, дисплей, комунікація) **MUST** інкапсулюватися у вигляді окремого C++ класу або модуля з мінімальною зв'язністю (low coupling).
- **Обґрунтування:** Це дозволяє легко тестувати код, замінювати апаратні компоненти та переносити прошивку на інші мікроконтролери без переписування всієї логіки.

## Governance

### 1. Amendment Procedure (Процедура внесення змін)
- Зміни до цієї конституції ініціюються через створення Pull Request або зміну специфікацій проєкту.
- Будь-яке пом'якшення вимог щодо безпеки чи ефективності пам'яті вимагає схвалення головного архітектора проєкту.

### 2. Versioning Policy (Політика версіонування)
- Версія конституції оновлюється за правилами Semantic Versioning:
  - **MAJOR:** Видалення або фундаментальна зміна основних принципів безпеки/пам'яті.
  - **MINOR:** Додавання нових принципів чи розширення інструкцій.
  - **PATCH:** Виправлення формулювань, друкарських помилок, уточнення текстів.

### 3. Compliance Review (Перевірка на відповідність)
- Кожен етап розробки (`/speckit-specify`, генерація або оновлення коду) перевіряється на відповідність цій конституції автоматично або під час code review.
